# План проекта под кейс «Созвездие» (Технонаставники)

Документ сверяет кейс из `Sozvezdie.pdf` с тем, что уже сделано в massa, и описывает,
что нужно доделать, чтобы сдать проект на максимум баллов.

---

## 1. Что требует кейс

**Задача.** MVP мессенджера для Android: регистрация по email и паролю, список чатов,
диалог, обмен сообщениями и изображениями в реальном времени.

**Форма результата.** APK + репозиторий на GitHub + README + видеодемонстрация +
защита 7 минут.

**Технические требования.**

| Требование | Значение |
|---|---|
| Платформа | Android 6.0 (API 23) и выше |
| Язык | Kotlin |
| Среда | Android Studio |
| Интерфейс | Jetpack Compose |
| Данные | Firebase Authentication, Realtime Database, Storage |
| Офлайн-история | Room |
| Сборка | APK, установка на устройство или эмулятор |
| Публикация | GitHub, README с запуском, стеком и структурой |

**Функциональный минимум (базовый уровень).**

1. Регистрация и вход по email/паролю.
2. Список диалогов и окно переписки.
3. Отправка, получение, обновление в реальном времени.
4. Отправка изображений из галереи или камеры.
5. Упрощённая отметка «прочитано».
6. Локальное сохранение истории для офлайн-доступа.

**Продвинутый уровень (даёт надбавку, если базовый стабилен).**

- голосовые сообщения;
- «печатает…», «в сети»;
- поиск по чатам;
- групповые чаты;
- доработанный современный UI.

**Регламент.** 6 занятий по 1 часу + онлайн-поддержка. Роли: студент-наставник
(тимлид) и школьник (разработчик).

**Баллы (100).**

| Раздел | Баллы |
|---|---|
| Презентация и защита | 25 |
| Функциональность мессенджера | 45 |
| Практическая ценность | 10 |
| Код и документация | 10 |
| Командная работа | 10 |

## 2. Проверка текущего проекта

Сейчас massa — это работающий веб-прототип: статический клиент (`index.html`,
`app.js`, `styles.css`) плюс свой сервер на Python (`server.py`) с базой в JSON и
файлами на диске, развёрнутый на VPS с HTTPS.

**Что уже есть и переносится в Android-версию практически один в один:**

| Возможность | Состояние | Куда идёт |
|---|---|---|
| Регистрация и вход по email/паролю | есть, PBKDF2, сессии 30 дней | заменяем на Firebase Auth |
| Список чатов, непрочитанные, сортировка | есть | ChatListScreen |
| Диалог: текст, время, автор в группе | есть | ChatScreen |
| Ответ на сообщение (свайп вправо, цитата) | есть | ChatScreen (жест) |
| Отметка «прочитано» / «отправлено» | есть, с правилом для групп | Firebase + RTDB |
| Фото, видео, файлы | есть, до 50 МБ | Firebase Storage |
| Группы: создание, фото, участники, профили | есть | GroupsScreen |
| Поиск людей и чатов | есть | SearchScreen |
| Избранное (заметки себе) | есть | можно сохранить как фичу |
| Настройки: тема, акцент, аватар | есть, сохраняются на сервере | SettingsScreen |
| Визуальный стиль | готов: плоские цвета, малые радиусы, квадратные аватарки, MASSA | Compose-тема |

**Чего кейс требует, а у нас нет:**

1. **Kotlin + Jetpack Compose + Android Studio** — сейчас это веб-страница.
2. **Firebase Auth / Realtime Database / Storage** — сейчас собственный сервер.
3. **Room и офлайн-история** — сейчас кэш в `localStorage` браузера.
4. **APK и репозиторий на GitHub** — сейчас деплой на VPS.
5. **Голосовые сообщения, «печатает…», «в сети»** — не реализованы.
6. Материалы защиты: видео и презентация.

**Вывод.** Проект не «с нуля»: есть продуманный UX, схема данных, правила
прочтения, работающие группы и файлы. Но сдавать нужно нативное приложение на
Firebase — поэтому основной объём работ — перенос на Kotlin/Compose и Firebase,
а не придумывание продукта.

## 3. Решение по стеку

**Основной путь — ровно по кейсу:** Firebase Auth + Realtime Database + Storage,
Room для истории, Compose для интерфейса, Kotlin, APK.

Почему так, а не «оставить свой сервер»:

- в критериях и рекомендациях наставнику прямо сказано показать, **где
  используются Authentication, Database, Storage и Room**;
- Firebase даёт синхронизацию в реальном времени «из коробки» — на 6 занятий это
  критично, свой сервер потребует SSE/WebSocket и времени на отладку;
- офлайн-история и кэш — штатные сценарии Firebase, меньше кода.

**Наш сервер остаётся как бонус.** На защите в разделе «практическая ценность»
показываем: тот же продукт умеет работать и на своём сервере (это уже работает
по адресу `https://50-114-115-15.sslip.io`), то есть команда понимает
клиент-серверную архитектуру, а не только SDK. Это закрывает критерий
«обоснованность формата локального сервиса» и выделяет на фоне других команд.

Итог: **демонстрируем Android-приложение на Firebase**, веб-версию показываем
30 секундами как «второй клиент того же продукта».

## 4. Архитектура Android-приложения

### 4.1. Модули и слои

```
app/
  data/
    auth/        FirebaseAuth-обёртка, регистрация, вход, выход, текущий uid
    db/          Realtime Database: chats, messages, users, presence, typing
    storage/     Firebase Storage: аватары и вложения
    local/       Room: сущности, DAO, база, репозиторий
    repo/        ChatRepository, MessageRepository, UserRepository
  ui/
    auth/        AuthScreen + AuthViewModel
    chats/       ChatListScreen + ChatListViewModel
    chat/        ChatScreen + ChatViewModel
    group/       NewGroupScreen, MembersScreen
    profile/     SettingsScreen
    theme/       MASSATHEME: цвета, типографика, формы
    common/      аватары, пузыри, время, состояния загрузки
  MainActivity, MassaApp (Application, DI вручную)
```

Архитектура — MVVM + Repository, один модуль `app`, без Hilt (на 6 занятий
лишняя сложность), зависимости через простой `AppContainer`.

### 4.2. Схема Realtime Database

```
users/{uid}/
  name, email, photoUrl, lastSeen, accent, theme

chats/{chatId}/
  type: "direct" | "group" | "saved"
  title, photoUrl, ownerId, createdAt
  members/{uid}: true
  lastMessage: { text, ts, senderId, kind }
  reads/{uid}: ts         // до какого времени прочитано

messages/{chatId}/{messageId}/
  senderId, text, ts, kind: "text" | "image" | "video" | "file" | "voice"
  fileUrl, fileName, fileSize, durationMs
  replyTo: { messageId, senderName, text }

typing/{chatId}/{uid}: ts          // «печатает…», живёт 5 секунд
presence/{uid}: { state: "online" | "offline", lastSeen }
```

Ключи чатов для личных диалогов — детерминированные (`uid1_uid2` по алфавиту),
чтобы не создавать дубликат при одновременном старте с двух сторон.

### 4.3. Room (офлайн)

Сущности: `ChatEntity`, `MessageEntity`, `UserEntity`.
Сообщение хранит `status`: `sending` / `sent` / `failed`.
Порядок: экран показывает данные из Room, сеть дописывает поверх (single source
of truth = Room, Firebase — источник обновлений).

Очередь отправки: `WorkManager` с экспоненциальной задержкой для `failed`.

### 4.4. Экраны

| Экран | Что на нём |
|---|---|
| AuthScreen | MASSA, вход/регистрация, ошибки, «глаз» у пароля |
| ChatListScreen | Избранное, чаты, аватары, превью, время, непрочитанные |
| ChatScreen | пузыри, ответы, фото/видео/файлы/голос, «печатает…», отправка |
| SearchScreen | поиск людей по имени/почте, свои чаты |
| NewGroupScreen | название, фото группы, выбор участников |
| MembersScreen | участники, профиль участника, добавить, выйти |
| SettingsScreen | аватар, имя, тема, акцент, выход |

### 4.5. Что берём из веб-версии как есть

- палитра и правила: плоские цвета, градиентов нет, скругления 2–6 px,
  квадратные аватарки, шрифт системный;
- сетка списка чатов и пузырей, поведение времени (24 ч, из `ts`);
- правило «прочитано»: в личном чате — когда прочитал собеседник, в группе
  больше двух — когда прочитали двое;
- тексты интерфейса (русские формулировки уже вылизаны);
- сценарий «ответ свайпом вправо», меню «Ответ / Кто прочитал»;
- экран участников с фото группы и добавлением людей.

## 5. План по занятиям

Формат: 1 час очно + домашка. Каждое занятие заканчивается проверяемым
результатом — это же требование кейса.

### Занятие 1. Каркас и авторизация-макет

**Наставник:** создать проект в Android Studio, подключить Compose и Firebase
(пустой проект в консоли), показать структуру, собрать тему MASSA.
**Школьник:** экран входа/регистрации без логики, навигация между экранами.
**Результат:** приложение запускается на эмуляторе, два экрана переключаются.
**Домашка:** прочитать про `ViewModel` и `StateFlow`.

### Занятие 2. Firebase Authentication

**Наставник:** объяснить Auth, показать включение email/пароля, разобрать ошибки.
**Школьник:** регистрация, вход, выход, сохранение сессии, `AuthViewModel`.
**Результат:** аккаунт создаётся, после перезапуска приложение помнит вход.
**Домашка:** экран «профиль» с почтой и именем.

### Занятие 3. Realtime Database: список чатов

**Наставник:** схема данных, правила безопасности, чтение одного узла.
**Школьник:** список чатов из `chats/{uid}`, превью последнего сообщения,
создание личного чата по email собеседника.
**Результат:** два аккаунта видят друг друга в списке, чат открывается.

### Занятие 4. Сообщения и Room

**Наставник:** `childEventListener`/`ValueEventListener`, модели, Room, порядок
синхронизации; показать подводные камни (дубликаты, порядок по `ts`).
**Школьник:** экран чата, отправка текста, реальное время, офлайн-история,
отметка «прочитано».
**Результат:** сообщения приходят мгновенно, история видна после перезапуска
без сети (авиарежим).

### Занятие 5. Файлы, Storage, полировка

**Наставник:** Photo Picker, загрузка в Storage, прогресс, сжатие картинок.
**Школьник:** отправка изображения из галереи и камеры, показ в пузыре,
аватары; доводит UI: пустые состояния, ошибки, загрузка.
**Результат:** фото уходит и приходит, APK собирается и ставится на телефон.

### Занятие 6. Продвинутый уровень и защита

**Наставник:** помочь с «печатает…», «в сети», поиском и группами; репетиция.
**Школьник:** одна-две фичи продвинутого уровня на выбор + презентация.
**Результат:** APK, репозиторий, README, видео, презентация на 7 минут.

**Онлайн-поддержка между занятиями:** разбор ошибок сборки, код-ревью, помощь
с Firebase Console.

реализованные функции (это отдельные 5 баллов).

## 10. Риски и что делать заранее

| Риск | Что делаем |
|---|---|
| Firebase-проект не дадут вовремя | создать свой бесплатный проект в первый же вечер, ключи в `google-services.json` не в git |
| Школьник не успевает | заранее подготовленный каркас (тема, навигация, модели) — он пишет экраны и логику |
| Версии Gradle/AGP конфликтуют | зафиксировать рабочий набор в README, не обновлять в середине |
| Эмулятор тормозит на школьном ноутбуке | тестировать на реальном телефоне по USB, эмулятор — как второй аккаунт |
| Нет второго устройства на защите | второй аккаунт в эмуляторе + заранее записанное видео |
| Интернет в аудитории плохой | демонстрация на мобильном интернете, офлайн-часть работает из Room |
| Правила безопасности Firebase слишком открыты | прописать `users/{uid}` — только владелец, `chats` — только участники |
| Android 6 (API 23) | minSdk 23, проверить, что Compose-зависимости не тянут API выше |

## 12. Безопасность

Подробный разбор — в [SECURITY.md](SECURITY.md). Коротко:

- на сервере уже включены HSTS, CSP, запрет фреймов, скрыта версия,

## 13. Что делаем с текущим веб-проектом

1. Оставляем как **референс дизайна и UX** — скриншоты идут в README и
   презентацию.
2. Оставляем как **второй клиент** для демонстрации «продукт умеет и на своём
   сервере» — работает сейчас на VPS.
3. Веб-клиент не развиваем: силы идут в Android-версию.
4. Если останется время после сдачи — переносим на веб-версии те же фичи
   (голосовые, «печатает…»), чтобы демонстрация была симметричной.
