# План подключения Firebase (VPS остаётся)

Документ описывает, как включить Firebase для massa, ничего не ломая на VPS.
Коротко: **Firebase — облако для данных и авторизации, VPS — хостинг, раздача
APK, резервный API и «свой сервер», который мы не выбрасываем.**

---

## 1. Что где живёт после настройки

```
Телефон / браузер (наш интерфейс)
        │
        ├── Firebase Auth            вход, регистрация, токены
        ├── Firebase Realtime DB     чаты, сообщения, прочтения,
        │                            «печатает…», «в сети»
        └── Firebase Storage         фото, видео, файлы
                 ▲
                 │  (не обязателен, но остаётся)
VPS 50.114.115.15
        ├── Caddy + HTTPS            хостит веб-версию
        ├── /opt/massa               код и статика
        ├── /var/lib/massa           данные СВОЕГО сервера (резерв)
        ├── Python API               запасной бэкенд, если Firebase недоступен
        └── раздача APK              /app/massa.apk
```

Ключевое: приложение работает с Firebase напрямую, VPS не проксирует Firebase.
Свой Python-сервер остаётся вторым бэкендом — переключатель в клиенте.

## 2. Что нужно сделать в консоли Firebase (10–15 минут)

1. `console.firebase.google.com` → **Add project**.
   Название: `massa` (projectId получится, например, `massa-1a2b3`).
   Google Analytics можно выключить — не нужен.
2. **Build → Authentication → Get started → Email/Password → Enable.**
   Остальные провайдеры выключены.
3. **Build → Realtime Database → Create Database.**
   Место: `europe-west1` (ближе к VPS и к пользователю). Режим: **locked mode**.
4. **Build → Storage → Get started.** Режим: **production mode**.
5. **Project settings (шестерёнка) → Your apps → Android**:
   - package name: `app.massa` (тот же, что будет в `applicationId`);
   - скачать `google-services.json`.
6. Там же **Your apps → Web** (`</>`): добавить приложение `massa-web`,
   скопировать объект `firebaseConfig`.
7. **Rules** (правила) — вставить из наших файлов:
   - Realtime Database → Rules → содержимое `firebase/database.rules.json`;
   - Storage → Rules → содержимое `firebase/storage.rules`.
8. **Project settings → API key** — ограничить ключ:
   Android-приложение `app.massa` + SHA-1 подписи; для веба — домены
   `50-114-115-15.sslip.io` и `localhost`.

## Что мне нужно прислать

Один из двух вариантов:

- `google-services.json` (для Android) и объект `firebaseConfig` (для веба), либо
- просто строки: `apiKey`, `authDomain`, `databaseURL`, `projectId`,
  `storageBucket`, `appId`, `messagingSenderId`.

`databaseURL` будет вида `https://massa-1a2b3-default-rtdb.europe-west1.firebasedatabase.app`.

## 3. Схема данных в Realtime Database

```
users/{uid}
  name, email, photo, accent, theme, lastSeen

chats/{chatId}
  type: "direct" | "group" | "saved"
  title, photo, ownerId, createdAt
  members/{uid}: true
  last/{text, ts, senderId, kind}

messages/{chatId}/{messageId}
  senderId, kind, text, ts
  replyTo/{id, text, author}
  attachment/{path, name, size, mime, duration}

reads/{chatId}/{uid}: ts            // до какого момента прочитано
unread/{chatId}/{uid}: n            // счётчик для бейджа
typing/{chatId}/{uid}: ts           // «печатает…», живёт 5 секунд
presence/{uid}/{state, chat, typing, ts}
```

Почему так, а не «всё в одном дереве»:

- сообщения отдельно от метаданных чата — не тянем всю переписку, когда нужен
  только список чатов;
- `reads` и `unread` отдельными узлами — правила проверяют их независимо;
- `typing` — временный узел, его пишут и стирают через `onDisconnect`.

## 4. Правила безопасности

Файлы уже готовы:

- [`firebase/database.rules.json`](../firebase/database.rules.json) — доступ
  к чату только участникам, `senderId` обязан совпадать с `auth.uid`,
  длина текста ≤ 4096, тип сообщения из списка, нельзя править чужие метаданные;
- [`firebase/storage.rules`](../firebase/storage.rules) — только авторизованные,
  лимит 50 МБ на файл, типы `image/*`, `video/*`, `audio/*`, `application/*`,
  аватары — только свои и до 2 МБ.

Ограничение по Storage, о котором надо знать: в правилах Storage нельзя
проверить участника чата из RTDB, поэтому чтение разрешено всем авторизованным.
Компенсация: имена файлов — UUID, ссылка выдаётся только через RTDB участникам.
Для учебного MVP это нормально; в проде — Cloud Functions с подписанными URL.

## 5. Клиент: что меняем

1. **Слой данных.** Сейчас `api.js` умеет `HttpBackend` (наш сервер) и
   `LocalBackend` (демо). Добавляем третий — `FirebaseBackend` с тем же
   интерфейсом: `signIn`, `signUp`, `sync`, `sendMessage`, `markRead`,
   `presence`, `getMembers`, `setChatAvatar`, `sendFile`.
   Интерфейс не меняется — экраны и стили остаются как есть.
2. **Переключатель бэкенда.** `?backend=firebase` или настройка в профиле;
   по умолчанию — Firebase. VPS-режим остаётся доступен.
3. **Офлайн.** Включаем кэш SDK; интерфейс уже лежит в APK, данные — в IndexedDB,
   очередь отправки — `ref.push()` с локальным кэшем (RTDB сам дошлёт при сети).
4. **«В сети».** `presence/{uid}` + `onDisconnect().set({state:'offline'})` —
   сервер сам поставит офлайн, когда телефон пропал.
5. **«Печатает…».** `typing/{chatId}/{uid} = now()` каждые 2–3 секунды, пока есть
   текст; `onDisconnect().remove()`; клиент показывает, если метке меньше 5 секунд.
6. **Прочитано.** `reads/{chatId}/{uid} = now()` при заходе в чат и раз в 3,5 секунды,
   как сейчас. Всё обновляется через `onValue` — без перезагрузки.
7. **Файлы.** Загрузка в Storage, в сообщение пишем `attachment.path`, ссылку
   получаем через `getDownloadURL` и кэшируем.

## 6. Перенос существующих данных

Пароли перенести нельзя: в нашем `accounts.json` лежат PBKDF2-хеши, а Firebase Auth
хранит свои. Значит:

1. **Аккаунты** — пользователи регистрируются заново (или создаём через Admin SDK
   со случайным паролем и ссылкой на сброс).
2. **Чаты и сообщения** — переносим скриптом:
   - выгружаем `state.json` с VPS;
   - скрипт (Python + `google-auth`) пишет данные в RTDB по REST с токеном
     сервисного аккаунта;
   - `uid` в Firebase совпадают с `uid` из списка аккаунтов — маппинг делаем вручную
     по почте, чтобы сообщения не потеряли авторов.
3. **Файлы** — перекладываем из `/var/lib/massa/files` в Storage
   (`chats/<chatId>/<uuid>`), путь подставляем в `attachment`.

Перенос делаем после того, как новый клиент заработает на тестовых данных.

## 7. Порядок работ

| Шаг | Что делаем | Время |
|---|---|---|
| 1 | Вы создаёте проект, включаете Auth/RTDB/Storage, присылаете конфиг | 15 мин |
| 2 | Вставляем правила, проверяем их в Rules Playground | 30 мин |
| 3 | Пишем `FirebaseBackend` (вход, чаты, сообщения, прочтения) | 1 день |
| 4 | Подключаем presence и typing через `onDisconnect` | 3–4 ч |
| 5 | Файлы: Storage, загрузка/скачивание, превью | 3–4 ч |
| 6 | Офлайн-режим и очередь отправки | 3 ч |
| 7 | Перенос данных (по желанию) | 2–3 ч |
| 8 | Тесты на двух устройствах, демонстрация в самолётном режиме | 2 ч |

Итого **2–3 дня** спокойного темпа.

## 8. Проверки после настройки

- вход и регистрация через Firebase Auth, ошибки показываются по-русски;
- сообщение доходит на второе устройство за секунду;
- «печатает…» и «в сети» работают, пропадание сети даёт «не в сети» за 15 секунд;
- «прочитано» появляется без перезагрузки;
- фото уходит в Storage и показывается в пузыре;
- правила: чужой чат читать нельзя (проверить через Rules Playground);
- самолётный режим: интерфейс открывается, история видна, отправленное уходит
  в очередь и досылается при появлении сети.

## 9. Риски и ограничения

| Риск | Что делаем |
|---|---|
| Бесплатный тариф Spark: 100 одновременных подключений, 1 ГБ в Storage, 10 ГБ скачивания в месяц | для школьного проекта с запасом; при росте — Blaze |
| Правила Storage не умеют проверять участника чата | UUID-пути, ссылки только через RTDB; в проде — Functions |
| Старые пароли не переносятся | перерегистрация или Admin SDK со сбросом |
| Firebase недоступен с сети пользователя | переключатель на наш VPS-бэкенд остаётся |
| Данные разъедутся между Firebase и VPS | VPS-режим после переезда — только для демонстрации, не для параллельной записи |
| Нужен интернет для синхронизации | офлайн-кэш + очередь, интерфейс из APK |

## 10. Что остаётся на VPS навсегда

- HTTPS для веб-версии и раздача APK;
- резервный API и наш собственный сервер данных (он уже работает);
- бэкапы, fail2ban, лимиты, заголовки безопасности;
- возможность демонстрации «у нас есть и свой сервер, не только Firebase» —
  это плюс к разделу «практическая ценность».
